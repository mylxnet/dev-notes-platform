## 现象

站点巡检工具的判定逻辑是：抓当前页面正文，和基线比哈希与逐行差异，不一致就发告警。

用户给某页加了忽略规则——把"日期"和"访问量"这类天天变的内容过滤掉。预期是下一轮就安静，实际结果：

```
下一轮巡检：内容变更
差异：2026-11-16 → 2026-11-17
```

必须手动点一次「设为新基线」才会停止告警。也就是说：**规则改了等于没改**。

## 排查

看比对用的两个值就明白了：

```js
// 抓取与过滤只作用于"当前文本"
const current = filterByRules(extracted.text, rules);

// 基线存的是当初抓到的"未过滤旧正文"
const baseline = baselineRecord.text;

sha256(baseline) !== sha256(current)   // 永远不等
```

忽略规则只在抓取时过滤当前文本，而基线里躺着的是**未过滤的原始正文**。于是：

- 哈希比对：`sha256(未过滤基线)` 与 `sha256(过滤后当前)` 必然不同；
- 逐行 diff：两侧文本形态不一致，差异行永远存在；
- 更隐蔽的是字数类规则：喂给"正文骤降/正文下降"判据的基线字数也是未过滤的，加了规则后当前字数变小，可能直接误判成"正文骤降"。

## 修复

原则只有一句：**比对前，用同一套当前规则把基线也过滤一遍。**

```js
// 用当前规则重新过滤基线正文，不改写原始记录
const baselineText = filterByRules(baselineRecord.text, rules);

const contentChanged = sha256(baselineText) !== sha256(current);
const diffLines = diff(baselineText, current);

// 字数类判据同样用过滤后的字数
const baselineChars = baselineText.length;
```

三点约束：

1. 只改"用于比对的那份副本"，**基线原文不落盘改写**——删掉规则就能恢复原状；
2. 哈希、差异、字数三类判据必须全部换成过滤后的值，漏一个就还是会对不上；
3. 规则改动即时生效，不再需要"重建基线"。

## 一个必须写在文档里的副作用

规则是双向生效的。如果某条规则误过滤了真实内容（比如把正文里的关键数字当成"访问量"），它**同时作用于当前文本和基线**，两侧一起被删掉，差异里反而看不出来——**可能掩盖真实变化**。

所以规则要写得足够窄（锚定结构或固定前缀），并且在界面上提示"规则过宽会掩盖变化"。

## 验证

- 加规则后不重建基线，下一轮巡检安静；
- 删除规则，历史内容差异恢复可见（说明基线原文没被改写）；
- 只在"当前文本"上造一处真实变化，加着规则也能报出来。

## 教训

1. **任何"过滤后的文本"与"历史快照"做比对，两侧都必须按同一规则处理**。只过滤一侧，规则改动就会表现成"必须重建基线"这种怪现象。
2. 派生指标（字数、行数、哈希）要跟着主文本一起改，否则修了 diff 却漏了阈值判断。
3. 不改写历史快照是条纪律：规则是可回退的，基线数据不该被规则污染。
4. 双向过滤会带来"掩盖变化"的风险，这类副作用要显式写进文档，而不是留给用户自己发现。
