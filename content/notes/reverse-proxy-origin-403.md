## 现象

原生应用装好，界面正常，登录页能打开。但首次初始化输入两遍密码点提交，返回：

```
403 跨站请求被拒绝
```

登录同样被拒。奇怪的是：同样的地址在浏览器里直接打开页面没问题，读接口也正常——**只有写操作全挂**。

## 排查

服务端做同源校验的逻辑很直接：取请求的 `Origin`，和 `Host`（或 `X-Forwarded-Host`）比对，不同就当成跨站。

打日志看这两个值：

```
Origin: http://nas.local:5666
Host:   localhost
```

对不上的原因不在代码，在链路：

![网关反代下 Origin 与 Host 对不上](/media/siteguard-origin.svg)

浏览器发出的 `Origin` 是它自己看到的地址（NAS 域名 + 端口）；而飞牛的统一网关把请求反向代理到 Unix Socket 时，会把 `Host` 改写成本地地址。两个值天然不可能相等，于是**所有写操作都被判成跨站**。

这也解释了"本地直连一直正常"：直连时 `Origin` 与 `Host` 同源，校验永远通过，问题只在挂到网关后面才出现。

## 修复：换一个跨站发不出的信号

思路不是"关掉校验"，而是换判据——用浏览器**能发、跨站发不出**的东西证明同源。

具体做法：前端每个 API 请求都带一个自定义头：

```js
fetch('/api/login', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'x-siteguard-client': '1'   // 自定义头
  },
  body: JSON.stringify(payload)
})
```

服务端见到这个头就视为同源页面请求，跳过 `Origin` 比对；**不带头的请求仍走原来的严格校验**，`ALLOWED_ORIGINS` 白名单照常生效。

## 为什么这样不降低安全性

关键在浏览器的两条约束：

1. **跨站 HTML 表单无法自定义请求头**。表单能提交的只有 `enctype` 决定的几种编码，加不了 `x-siteguard-client`。
2. **跨站 `fetch` 带自定义头会触发 CORS 预检**。预检是 `OPTIONS` 请求，本服务不返回任何 CORS 头，浏览器直接把正式请求拦下——请求根本到不了业务代码。

所以这个头实际上是"同源页面才有资格发出的令牌"，强度等价于一个 CSRF token，但不用维护 token 生命周期。

## 验证

- 实机：重新出包、装好后初始化与登录正常；
- 反向验证：不带该头的写请求仍然 403（说明严格校验分支还在）；
- 跨站验证：从另一个源的页面提交表单，仍然被拒（说明放宽只对带头的请求生效）。

## 教训

1. **在网关/反向代理后面，`Origin` 与 `Host` 不能作为同源判定的唯一依据**。它们描述的是链路不同位置的事实。
2. 判定同源要用"跨站发不出来的信号"：自定义请求头、CSRF token、双提交 Cookie 都是这个思路。
3. 放宽要**精确到分支**，而不是全局关掉开关——"带头跳过、缺头严格"这种写法，既能修好网关场景，又不牺牲直连场景的防护。
4. 这类缺陷有个固定特征：**读接口正常、写接口全挂**。看到这个组合，先怀疑同源/CSRF 校验，而不是业务逻辑。
