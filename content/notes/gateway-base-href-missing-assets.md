## 现象

原生应用装好，从桌面图标打开，页面**结构出来了但没有样式**：标题文案裸露在最上方，登录卡片没渲染，浏览器控制台里两条 404。

而同一个服务在本机直接访问（`http://127.0.0.1:端口/`）完全正常，样式、脚本都在。

## 排查

看 404 的 URL：

```
GET /app/style.css   404
GET /app/app.js      404
```

再看实际的页面地址：`/app/siteguard`——**没有尾斜杠**。

浏览器的规则是：`/app/siteguard` 会被当作"文件名"，页面里的相对路径 `style.css` 就此解析成 `/app/style.css`；而网关只转发 `/app/siteguard/*` 前缀下的请求，于是两个资源都 404。

`app.js` 没加载，所以由脚本渲染的登录表单自然也不出现——这也解释了为什么"结构在、表单不在"。

本地直连时入口是 `/`，相对路径解析到根，因此这个问题在本机永远测不出来。

## 修复

三个方向评估过：

| 方案 | 结论 |
|---|---|
| 改 `app/ui/config` 里的 url 加尾斜杠 | 只能管到新入口，用户手敲不带斜杠的地址还是坏 |
| 把 HTML/JS 里的相对路径全改成绝对路径 | 耦合写进产物，换前缀就得重新打包 |
| **服务端返回 HTML 时按请求路径注入 `<base>`** | 采用 |

实现就是在下发 `index.html` 时插一行：

```html
<!-- 网关下：按实际请求前缀注入 -->
<base href="/app/siteguard/">
<!-- 直连根路径时注入 / -->
<base href="/">
```

这样 URL 带不带尾斜杠都能正确解析资源，且不用改一行业务代码。

配套还要改一处 CSP：原来 `base-uri 'none'` 会禁止 `<base>` 生效，需要放开成 `base-uri 'self'`。这条很容易漏——注入的标签明明在 HTML 里，浏览器却当它不存在，多半是 CSP 拦了。

## 验证

复测方式要模拟真实入口，而不是只测根路径：

- 启动时带上 `GATEWAY_PREFIX=/app/siteguard`；
- 在浏览器里分别打开**带尾斜杠**与**不带尾斜杠**的两个地址，确认 CSS/JS 都是 200、登录表单正常渲染；
- 打包后还要再跑一次，因为静态资源是随包分发的，源目录复制漏文件同样会 404。

## 教训

1. **网关类应用必须按"真实入口 URL"验证**，尤其是带不带尾斜杠这两种形态。本机根路径测试通过，什么都说明不了。
2. 相对路径的解析基准是可变的，`<base>` 是把这个基准显式化的最低成本手段；把绝对路径硬写进产物是反方向。
3. 注入 `<base>` 后如果没生效，先查 CSP 的 `base-uri`，再查 HTML 是否真的被替换。
4. 这类问题会伪装成"样式没打包进去"，实际资源请求根本没到服务端——先看 404 的完整路径，比翻构建脚本快。
