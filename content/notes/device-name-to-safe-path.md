## 为什么要防

LanFileShare 的目录结构是「共享区 + 设备区」，设备区按手机型号建子目录：

```
shared/
  devices/
    iPhone 15/
      2026-11-17/
    小米14/
      2026-11-17/
```

而"型号"是浏览器报上来的。请求体、UA、`userAgentData` 都是客户端可控字段——如果直接拿它当目录名，就等于让外部输入参与路径拼接。

## 四层处理

**第一层：型号白名单。** 只接受符合规则的型号字符串：字母、数字、中文、空格、`-`、`_`、`+`、`.`、`()`，长度不超过 64，出现路径分隔符或 `..` 一律拒绝，非法时回退成 `UnknownDevice`。这层挡的是"型号里塞路径"。

**第二层：目录名净化。** 即便型号通过了白名单，仍统一过一遍 `SanitizeFolder`：

- 非法字符替换成 `_`；
- 去掉首尾的点和空格（Windows 不允许目录名以点或空格结尾，`TrimEnd` 不做会导致创建失败或奇怪行为）；
- 结果若是**纯点**（`.`、`..`、`...`）直接拒绝——这一步很关键，白名单允许 `.`，而 `..` 恰恰是路径穿越的经典写法。

**第三层：路径归一化校验。** 拼接出候选路径后，用 `Path.GetFullPath` 归一化，再断言它仍在设备根目录之下：

```csharp
var full = Path.GetFullPath(candidate);
var root = Path.GetFullPath(deviceRoot) + Path.DirectorySeparatorChar;
if (!full.StartsWith(root, StringComparison.OrdinalIgnoreCase))
    throw new InvalidOperationException("路径越界");
```

这层是最后的兜底：前两层是"规则"，这层是"结果校验"，规则写漏了它还能拦住。

**第四层：文件名净化。** 目录名安全不代表文件名安全：

- 以 `_` 开头的文件名加前缀，避免在 macOS 侧被当成隐藏文件；
- **双扩展名拒绝**（如 `.bat.pdf`、`.exe.jpg`），避免下载后按第一个扩展名被误执行；
- 保留字符（`< > : " | ? *`）替换成 `_`；
- 超长时保留扩展名截断主体并追加短哈希，防止同名碰撞。

## 一个容易混的地方

型号虽然是"白名单过了一遍"，但目录名和文件名是两个不同的攻击面：白名单只管内容字符集，不管长度、不管首尾、不管是否纯点；而文件名还要考虑扩展名语义与跨平台差异。

所以校验不能收敛成"一个函数管两种名字"，否则总有一边被放松。

## 教训

1. **凡是进入路径拼接的字符串，都要有"结果校验"而不只是"规则校验"**——规则会写漏，`GetFullPath` 的边界断言不会。
2. 纯点名（`..`、`...`）是个高频漏点：字符白名单允许 `.`，语义上却绝不能当目录名。
3. 双扩展名是"看起来无害"的那类风险，单靠文件类型判断拦不住，得在命名阶段拒绝。
4. 跨平台细节要一次性写进净化函数：Windows 的尾部点/空格、macOS 的隐藏文件前缀，分散处理必然漏。
