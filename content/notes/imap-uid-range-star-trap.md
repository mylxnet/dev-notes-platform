## 现象

后台轮询上线当天，通知铃铛就有反应了：每轮都提示「收到新邮件」。点进去，列表里那封邮件是三天前就存在的、已读的信。

这个毛病在轮询上线之前也有，只是手动刷新频率低，一次闪一下也就过去了。改成每分钟一跳之后，它变成了一条稳定复现的噪音。

## 从一行守卫说起

增量同步靠一个游标：记住上次同步到的最大 UID，下次从它的下一封开始。

```ts
if (fromUid > uidNext) return { added: 0, newIds: [] }
```

`uidNext` 是服务器给的「下一个 UID」，`fromUid` 是本地游标算出来的起点。看起来只要起点超过下一个 UID，就说明没新信。

但游标对齐时，两个值是**相等**的：

```
lastUid = 最大 UID      = 4821
uidNext = 最大 UID + 1  = 4822
fromUid = lastUid + 1   = 4822
```

`4822 > 4822` 是假。守卫放行，代码继续往下走 `fetch('4822:*')`。

## `*` 不是「从这里往后」

IMAP 的区间不是「起点到最新」的意思，它是「两个 UID 之间」，而 `*` 的定义是**邮箱里的最大 UID**。而且区间两端**顺序无关**，服务端按 `min:max` 处理。

于是：

| 写法 | 服务端的理解 | 实际返回 |
|---|---|---|
| `4822:*`（本意：一封都没有） | 4821–4822 | 4821，也就是那封早就存在的信 |
| `4822:4999` | 4822–4999 | 空 |
| `4822:*`（真有 4830 时） | 4822–4830 | 4822~4830 |

`*` 只是「最大 UID」的别名，不会因为你想「从某处往后」就自动变成上界。想让「没新信」真的返回空集，守卫必须写成 `>=`：

```ts
if (fromUid >= uidNext) return { added: 0, newIds: [] }
```

## 拿回来的那封被算成了「新增」

放行之后，4821 是已存在的记录，走 existing 分支。而这个分支里写着：

```ts
existingIds.push(...)
added += 1        // ← 问题在这
```

`added` 的本意是「本次新建了几条记录」，但已存在的分支也给它 +1。三件事串起来：

1. 一封老信被计成新增 → `totalNew > 0`；
2. 收尾 `if (totalNew > 0) push('new_mail')` → 推一条通知；
3. 通知层对 `new_mail` **没有任何去重**——只有账号失败那一类做了「文案没变就不重复推」。

三项叠加，就是每轮一条通知。Gmail 还会放大它：同一封信同时挂在 `INBOX` 和一个自定义标签下，两个文件夹各命中一次，一次 `+2`。

## 修复

改动很小，但每一处都得想清楚语义：

- 守卫 `>` → `>=`；
- existing 分支删掉 `added += 1`，`added` 收窄为「本次新建 Message 条数」；
- 顺手补了「只对增量新建邮件预取正文」，避免对老信做无用功。

复跑 30 分钟节拍：`totalNew` 恒为 0，通知一条没多。手动发一封新信，通知恰好 1 条、列表恰好多 1 封。

## 顺带挖出来的隐患

最新那封信如果 `Message-ID` 缺失，去重逻辑 `findFirst(accountId, messageId)` 匹配不上任何记录，于是每轮都会 `create` 一条新行。跟上面同一个根源——每轮都会把最新那封重新捞一遍。

守卫修好之后这条也一起消失了。但它没有单独的回归用例，属于「顺带修掉」：理论上换个触发条件（手动刷新和轮询撞在同一封缺 ID 的邮件上）还能复现。

## 三条

- `uidNext:*` 是个陷阱。`*` 是最大 UID、区间无序，这个写法永远不会返回空集。
- 变量的名字就是它的语义边界。叫 `added` 就只能统计新建，混进一次「已存在」的计数，最后会以用户可见的方式露出来。
- 上游少算一格不可怕，可怕的是下游没有去重。任何「每轮都会跑」的路径，通知必须自己扛得住重复。
