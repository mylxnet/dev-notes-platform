## 旧做法为什么不行

服务端解析 `multipart/form-data` 时，最省事的写法是：请求头里有 `Content-Length`，那就 `new byte[bodyLength]`，把整个请求体读满再解析。

问题在于 `multipart` 的体积约等于文件体积：

| 文件大小 | 旧实现峰值内存 |
|---|---|
| 20 MB | 约 60 MB |
| 200 MB | 超过 600 MB |

多份缓冲叠加（整包 + 解码 + 落盘）之后，一台小内存机器传几个大文件就会触发内存压力；而且失败时用户看到的只是"传一半断了"。

## 新做法：固定窗口

改成**固定 1 MB 的滑动窗口**，每次从 socket 读一块、在窗口内解析、把已消费的数据移出窗口，再继续读。内存占用与文件大小彻底脱钩，只与窗口大小有关。

状态机四个状态：

```
WaitingForBoundary
    → ReadingPartHeaders
    → ReadingPartBody
    → WaitingForNextBoundary
```

三条实现纪律：

1. **消耗即消费**：窗口里的数据一旦被解析出来，必须立刻移出（或标记已消费），否则服务器还在等这些字节"被读完"。
2. **边界状态要跨窗口传递**：不能每读一块都从窗口开头重新扫 `--boundary`，否则大文件会被反复扫描成 O(n²)。
3. **只复制窗口内的完整片段**：跨窗口的边界字符要拼上下一块再判断，不能"看到半个边界就当命中"。

## 踩到的死锁

第一版上线后出现一个很难复现的现象：传大文件时**界面一直转圈，内存不涨，日志停在某个进度不再前进**。

根因在"发现终止符"那条分支：

```csharp
// 错误写法：终止符已经完整落在窗口内，却 break 回外层继续 await 下一块
if (foundTerminator) {
    break;   // ← 外层循环等的是"下一块数据"
}
```

终止符已经是这个请求的全部内容了。跳出循环去等下一块，就变成：**客户端在等服务端响应，服务端在等客户端发数据**。两边都在等，谁也不动，内存也不会涨——正是观察到的样子。

修复很轻：终止符命中后不要 `break`，改成 `continue`，带着已经排队的结束事件把本轮处理完，让状态机正常收尾。

## 代价

这套方案不是免费午餐：

- 每块数据多一次 `Array.Copy`（窗口搬移）；
- 每次重新扫描缓冲区，上界是一次 1 MB；
- 状态机复杂度明显高于"整包读满再解析"，边界判断必须写测试用例覆盖。

换来的是：**内存上限不再由用户的上传文件大小决定**。

## 教训

1. 流式解析里，**凡是"已经看到结尾"的分支都不能跳出循环去等更多数据**——这是死锁最典型的形状。
2. 内存优化要看峰值而不是平均值：整包读取的平均占用看着还行，峰值才是打垮机器的那一下。
3. 这类 bug 的表征很迷惑（不涨内存、不报错、只是不前进），先怀疑"两个进程/两端都在等对方"，比怀疑内存泄漏效率高。
