## 规则本身

| 操作 | 是否允许 | 原因 |
|---|---|---|
| 新增收入/支出 | 允许，且联动更新银行存款与科目余额 | 业务入口 |
| **编辑流水**（金额、摘要、科目、日期） | **禁止** | 编辑无法留下原始值，事后无法解释差异 |
| 作废流水 | 允许，联动**整体回滚**到操作前状态 | 等价于「这笔业务没发生」 |
| 删除流水 | 不提供 | 删除会连痕迹一起去掉 |

编辑功能不是「暂时没做」，是**明确禁用**：后端 `PUT /api/transactions/:id` 只接受 `status: 'voided'`，其余字段一律返回 `403 TXN_READONLY`；前端把原来的编辑弹窗改成只读详情视图，只留「作废 / 撤销作废」两个按钮。

## 为什么值得这么设计

记账类系统里，「改一笔」和「作废一笔再记一笔」在数据库层面差别不大，但在**可追溯性**上天差地别：

- 编辑：原值被覆盖，除非专门做字段级历史，否则事后没人说得清这笔账原来是多少；
- 作废 + 重记：两条记录、两条操作日志，`old → new` 全在，任何时点都能重建当时的账面。

配合「所有修改型操作写操作日志（字段级 old→new，保留 48 小时）」，作废路径天然满足留痕要求，编辑路径则要额外做一套快照机制才等价——不如不做。

## 作废必须整体回滚

单点回滚会留下一半的状态，所以作废走的是完整反算：

```
记一笔支出：银行存款 - / 科目余额 -   （校验余额 ≥ 0，不足直接拒绝）
作废该笔：  银行存款 + / 科目余额 +   （回到操作前）
```

同理，收款核销作废时，除了核销记录 `normal → voided`，还要：

1. 应收单已收减少、待收恢复；
2. 应收状态回退（`closed → open`，或保持 `partial`）；
3. 该单位 `outstandingCents` 重新汇总；
4. 现金核销对应的收入流水同步作废（银行存款回退）；抵销核销则不动流水。

四步缺一步，账面上就会出现「钱回来了但应收没变」这类幽灵差异。

## 连带的防负校验

既然不允许事后编辑金额，那么**记错方向的风险就必须在入口拦住**。所以支出侧加了余额校验：

```
当前银行存款 = 期初 + 收入合计 - 支出合计
支出金额 > 当前余额 → 400 INSUFFICIENT_BALANCE（提前拒绝，不落库）
```

## 这套规则的已知边界

- 转账类流水当时仍可编辑（未纳入限制），后续应参照流水改成只读；
- 余额防负只覆盖「直接记支出」，核销、转账等入口尚无同等校验；
- 操作日志只留 48 小时，超过窗口的历史差异只能靠流水与作废记录本身解释。

## 一句话总结

**把「改」变成「作废 + 重记」，用多一步操作换一条永远可解释的账。** 这条规则的成本落在交互上，收益落在对账与审计上——对记账系统来说，这笔交易划算。
