## 现象

LanFileShare 早期用 `HttpListener` 起服务。绝大多数机器正常，但在极少数环境里会出现一种很别扭的状态：

- 服务启动成功，日志里打印了端口；
- `netstat` 看端口确实是 `LISTENING`；
- 浏览器打开地址，转圈，然后超时；
- 进程自己完全收不到请求。

## 排查

把监听端口的**属主**打出来，问题就清楚了：

```
TCP    0.0.0.0:50080    0.0.0.0:0    LISTENING    4
```

PID 4 是 `System`。也就是说，这个端口不是我们的进程在对外服务，而是被 `http.sys` 内核驱动接管了。

`HttpListener` 并不直接在用户态监听套接字，它把 URL 前缀注册给 http.sys，由内核统一接收再回灌给注册者。当前缀被 URL 保留项、其他注册者或残留状态占住时，注册可能"看起来完成"而实际没拿到；包被路由到内核队列后归属 System，进程侧永远等不到。

这也解释了为什么它只在少数机器上出现：取决于那台机器上装了哪些占用 http.sys 前缀的软件、以及之前有没有别的实例非正常退出。

## 决策

评估下来有三条路：

| 方案 | 结论 |
|---|---|
| 换端口重试 | 治不了根，前缀占用与端口无关 |
| 用 IIS/反向代理托管 | 局域网免安装场景不合适，多一层依赖 |
| `TcpListener` 自研用户态 HTTP | 采用 |

自研的代价是解析要自己写，但换来两件事：端口一定在**自己进程**手里，且不依赖 http.sys 的注册状态。

## 实现要点

- 只实现 HTTP/1.1 够用的子集：请求行、请求头、`Content-Length` 定长读取、`Connection: keep-alive`。
- 端口不再固定 8080：优先在 `50000–50999` 区间随机尝试，全失败才回退到 8080，启动日志里写明**实际绑定**的端口。
- 并发上限 64 连接，其中单请求处理线程池 4 并发，防止大量小文件把线程池打爆。
- 提供 `/health` 自检端点，一条 `curl` 就能确认"是否真的能服务"。

## 验证

判据从"端口在听"改成"真的打一次请求"：

```bash
# 启动后自检，返回 200 才算成功
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:<实际端口>/health
```

自动化测试里这一层也有覆盖：自检用例会在真实 socket 上跑，而不是只调内部函数——用的就是这条判据。

## 教训

1. **端口 LISTENING 不等于你的进程在服务**。先看端口属主（PID），再看业务日志。
2. 涉及内核转发的组件（http.sys、端口保留、URL ACL）失败时经常**不给错误码**。这类组件要么绕开，要么必须在启动后做一次真实请求自检。
3. 自研协议层的成本要提前算清：这里能接受，是因为局域网场景只需要 HTTP/1.1 子集，且不打算支持 TLS。
