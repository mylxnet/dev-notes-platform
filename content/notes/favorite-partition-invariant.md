## 背景

剪贴板历史里有两种删除语义：

- 「清除」：清掉普通条目，**收藏必须保留**；
- 「取消收藏」：把这一个条目的收藏标记翻回去。

为了少存一份索引，内存里的条目数组维护了一个不变式：**收藏项全部在数组前段，非收藏项全部在后段**。删除范围靠一个派生量定位：

```cpp
// 收藏区长度 = 收藏项数量（依赖上面的分区不变式）
size_t Boundary() const {
    return static_cast<size_t>(std::count_if(items_.begin(), items_.end(),
        [](const Item& it) { return it.isFavorite; }));
}

// 清除：抹掉收藏区之后的所有条目
items_.erase(items_.begin() + Boundary(), items_.end());
```

只要不变式成立，`Boundary()` 就是收藏区的真实边界，这段删除是安全的。

## 问题

全面审查时发现表格批量导入会破坏这个不变式。

`AddFromClipboard()` 的插入逻辑是：先算出 `at = Boundary()`，把整批新条目从该点插入。正常情况整批都是非收藏项，插在边界上正好接在非收藏区开头，不变式成立。

但表格会逐格去重。去重时如果某一格命中了历史收藏，会把那条的收藏标记**迁移**到新条目上。于是这一批里就混进了 `isFavorite=true` 的项，而插入仍然按单元格顺序整批落位——收藏项就可能落在非收藏区的中间。

后果很具体：

1. `Boundary()` 返回"收藏数量"，但它不再等于"收藏区长度"；
2. `ClearAll()` 用这个值作为抹尾的起点，**保留的是非收藏、删掉的是收藏**——与需求正好相反；
3. `EnforceLimit()` 的末位淘汰与 `MoveToBack()` 的沉底同样依赖这个不变式，一起受波及。

## 修复

在批量插入之后、容量收敛之前，把分区重新整理一次：

```cpp
items_.insert(items_.begin() + at, fresh.begin(), fresh.end());
ApplyOrder();       // stable_partition：恢复 [收藏 | 非收藏]，整批皆非收藏时是幂等 no-op
EnforceLimit();
```

`ApplyOrder()` 本来就是「切换收藏」路径在用的重整函数，这里复用它，不新增语义。

## 回归用例

关键不是"加了个断言"，而是**断言必须能失败**。这条用例一共验四件事：

1. 批量插入后分区仍然成立（收藏全在前段）；
2. `ClearAll()` 之后收藏项仍然存在；
3. 落盘后重新加载，分区依然成立；
4. `Reset()` 之后同样成立。

然后做**负向对照**：把 `ApplyOrder()` 临时注释掉再跑。结果这一条用例 **8 项断言转红**，`ClearAll()` 之后收藏 `x` 真的被删掉了——证明断言确实在守这条不变式，而不是恒真。

## 教训

1. **不变式必须在"每一条写入路径"上重建**，不能只在编辑操作里做。批量插入看起来是原子的，却恰恰是唯一能让收藏项落到中段的路径。
2. **派生量（`Boundary()`）与真实分区不一致时，破坏的是"删谁"这种不可逆动作**。所以断言要写"删完收藏还在"，而不是"顺序对不对"。
3. **回归用例必须做负向对照**，否则分不清"断言真的在守"和"断言恒真"。
4. 与之对照的另一条经验：展示层"下次刷新自然收敛"是可接受的契约（例如点了收藏，该行留到下次刷新才移出）；但**数据层的不变式不行，它必须当场成立**。两者混为一谈，就会在不可逆的地方留下缺口。
