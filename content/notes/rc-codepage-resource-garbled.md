## 现象

实机走查拍到一张气泡截图：正文「填表接力已开启 / Alt+左键点输入框 = 把列表第一行贴进去……」逐字正常，**标题却是乱码**：

```
SuperClip è¶…çº§å‰ªè´´æ…
```

同一时间用文件属性读构建产物，`ProductName` 与 `FileDescription` 是同一串乱码，而 `FileVersion`、`ProductVersion`、`CompanyName` 全部正常。

## 排查

"正文对、标题错"这个组合很有指向性：正文来自代码里的字符串字面量，标题来自 exe 的资源与版本信息。也就是说，问题在资源侧。

打开资源脚本 `src/res/app.rc`，内容本身是正常的 UTF-8 中文：

```rc
VALUE "FileDescription", "SuperClip 超级剪贴板"
```

再看构建链：资源由 `windres` 编译。它默认按**输入代码页**读源文件，而不是按 UTF-8。在非中文的构建环境里，这个默认值是 CP1252——于是它把 UTF-8 的每个字节当成一个 Latin-1 字符，再宽化成 UTF-16 写进资源。`超级剪贴板` 的 15 个 UTF-8 字节，就这样变成了 15 个"看着像乱码"的字符。

C++ 侧不受影响：`L"…"` 走的是 g++ 的 UTF-8 源字符集，编译正常。**只有 `.rc` 里的字符串是坏的。**

那为什么直到这时才被发现？因为 Windows 10/11 把传统气泡转成 toast 时，标题位取的是 exe 的 `FileDescription`，而不是结构体里的 `szInfoTitle`。这个从几个版本前就存在的资源缺陷，第一次有了用户可见的出口。

还有一层：**这类缺陷只在构建机的 ANSI 代码页不是 936 时露脸**。中文 Windows 上 CP936 恰好把 `超级剪贴板` 的 15 字节两两配回 5 个汉字，"看起来是对的"。而项目走 WSL 交叉构建（locale 为 C/POSIX，落到 CP1252），所以它一直在坏，只是没人读那个字段。

## 修复

在 `app.rc` 顶部加一条代码页声明——**必须是文件的第一条指令**，要放在 `#include <windows.h>` 之前：

```rc
#pragma code_page(65001)
```

`windres` 与 MSVC 的 `rc.exe` 都认这一条，产品逻辑一行没改。

同时登记了另外两档方案备选：给 `CMAKE_RC_FLAGS` 加 `-J utf-8`（只修 mingw，MSVC 侧仍按本机编码吃源文件，属于半修）；资源串改纯 ASCII（两套工具链都不再依赖编码，代价是属性面板与任务管理器里没有中文名）。最终选第一条。

## 验证

判据不能是"看起来改了"，而是**从产物里把字符串按码点读回**：

| 字段 | 修复前 | 修复后 |
|---|---|---|
| `FileDescription` | 23 字符，`00E8 00B6 2026 …` | 15 字符，`8D85 7EA7 526A 8D34 677F`（超级剪贴板） |
| `LegalCopyright` | `©` 为 `00C3 00A9` | `00A9` |

顺带注意：控制台文本不能当编码证据。修好之后第一次读回，`FileDescription` 在 cp936 管道里显示成 `SuperClip ??????`，看着像没修好——只有把每个字符的码点打印出来才作数。

## 教训

1. **资源文件的编码属于构建配置**，和源清单一样只能有一处权威声明。源文件"看起来是 UTF-8"不算。
2. 用户可见的文本要有一条"从产物读回字符串"的判据。原来的版本信息判据只核了版本号三个字段，从没比对过 `ProductName`。
3. **新增可见界面会把老缺陷第一次照出来**。加气泡提示时，顺手把它读到的每个字段都拍一遍。
4. 编码问题会在控制台上伪装成"没修好"，也会在中文系统上伪装成"本来就没问题"——判据要么打码点，要么别下结论。
