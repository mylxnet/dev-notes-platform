## 一张表说明问题

系统里「收到投资收益」这一个动作，同时触碰五处状态：

| 对象 | 变化 |
|---|---|
| 银行存款 | + 金额 |
| 科目余额 | `投资收益 / <单位>` 子科目 + 金额 |
| 应收单 | 已收 +、待收 − |
| 核销记录 | 新增一条 `receipt(method='cash')` |
| 操作日志 | 一条字段级 `old → new` |

联动一多，靠记忆写代码必然漏。所以做法是先把全部联动**写成一张表**（记一笔、快速记账 12 个模板、科目、应收、投资 532 分配、流转费、引导页、备份、日志共九类），再拿这张表去逐条对代码。

## 校验怎么做的

两轮，口径一致：文档每一节 → 找到对应实现 → 用真实请求验证结果，而不是只看代码「看起来写了」。

```
第二轮覆盖 6 条变更规则 + 11 条既有规则
结果：变更项全部「已实现」，既有项全部「符合」
```

## 抓出来的六个真问题

核对过程中发现的，都不是"代码风格"问题，而是会算错账的：

| # | 问题 | 根因 |
|---|---|---|
| 1 | 引导页设了科目期初，科目余额一直是 0 | 接口只存了 `openingBalanceCents`，没同步 `balanceCents` |
| 2 | 引导页银行期初怎么填都不生效 | 前端发 `bankBalanceCents`，后端要 `bankOpeningBalanceCents`，字段名对不上 |
| 3 | 重名单位提示只有一句「请求失败 (409)」 | HTTP 封装只取了错误字符串，把 `status` 和响应体丢了 |
| 4 | 重名提示不告诉用户撞了哪个名字 | 前端没做 409 分支 |
| 5 | 同一问题在两个页面各犯一次 | 引导页与往来页是两套保存逻辑 |
| 6 | 引导页「查找或创建科目」永远返回 `null` | 内部调用漏了 `await` |

第 3、4 条值得单独说：错误信息丢失是**基础设施级**问题。`http.ts` 一开始只 `throw new Error(message)`，导致所有需要区分状态码的交互（重名、锁定、余额不足）都退化成一句通用提示。补上 `err.status` 与 `err.response` 之后，各页面才能按错误码给出具体文案。

## 校验的价值在哪

两轮核对下来，最有价值的产出不是「全部符合」这个结论，而是：

1. **文档与代码同时被校准**。规则文档升到 v1.6，代码也跟着改；
2. **发现了文档没写的隐性约定**，比如「引导页与普通入口的建单位联动收敛在后端同一个事务里」，之前只在实现里存在；
3. **量化了剩余风险**：转账仍可编辑、532 锁定只按年度判断、余额防负只覆盖直接支出——三条都明确写进文档，而不是等线上撞到。

## 顺手沉淀的两条做法

- **联动规则表要写「副作用」，不只写「正常路径」**。例如「作废现金核销」一节，写清四步回退（核销记录、应收单、单位汇总、收入流水），比写「作废后恢复」有用得多。
- **校验要做成可重复的动作**。文档顶部记了校验日期与轮次，第二次校验只覆盖变更项、回归既有项，成本可控。

## 一句话

联动复杂度压不下去时，**把规则落成表、把表拿去对代码**，比继续在脑子里推演可靠。两轮下来抓到的六个问题，任何一个留在线上都是账目错误。
